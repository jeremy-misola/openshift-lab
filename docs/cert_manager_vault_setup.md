# cert-manager → Vault PKI Integration

## 1. Objective

Wire the OpenShift cert-manager operator to HashiCorp Vault's existing PKI hierarchy (`pki_root` → `pki_int`, see `docs/vault_pki_setup.md`) so that `Certificate` resources on the Hub can be issued and auto-renewed from Vault instead of being generated by hand. This lets any Route behind the Hub's default IngressController (Grafana, ArgoCD, custom apps, etc.) inherit a browser-trusted cert without per-app Vault interaction.

Scope covered here: Vault's Kubernetes auth method, the cert-manager `ClusterIssuer`, an example `Certificate` for the apps wildcard, and the GitOps RBAC problem that surfaced while syncing these through Argo CD.

## 2. Architecture Context

- Vault (Docker container, `192.168.0.201:8200`) already runs a 2-tier PKI: `pki_root` (root CA) signs `pki_int` (intermediate). The role `homelab-cert-role` under `pki_int` is scoped to `allowed_domains=jeremymr.dev`, `allow_subdomains=true`.
- Vault runs **outside** the OpenShift cluster (Docker Compose on the Proxmox infra host), not as an in-cluster pod. This matters: Vault cannot use an in-cluster identity to validate Kubernetes ServiceAccount tokens, so it needs an explicit reviewer token (see 3.2).
- cert-manager is installed via the Red Hat "cert-manager Operator for Red Hat OpenShift" (OLM Subscription in `cert-manager-operator` namespace). **The operator and the actual controller run in different namespaces** — the Subscription/OperatorGroup live in `cert-manager-operator`, but the controller pods (and their ServiceAccount) run in `cert-manager`. Always verify with `oc get sa -n cert-manager` before binding a Vault role to a name/namespace — don't assume it matches the operator's own namespace.
- The Hub is managed via OpenShift GitOps (Argo CD) using an `ApplicationSet` (`operators/values/hub.yaml`). Anything applied through Argo CD is subject to whatever RBAC the `openshift-gitops-argocd-application-controller` ServiceAccount has — which by default does **not** include arbitrary CRDs added later by other operators (see Section 6).

## 3. Phase 1: Vault Kubernetes Auth Method

### 3.1 Enable the auth method
```bash
vault auth enable kubernetes
```

### 3.2 Create a reviewer ServiceAccount so Vault can call TokenReview

Because Vault runs outside the cluster, it must authenticate itself to the Kubernetes API just to validate *other* tokens. This is a one-time setup, independent of cert-manager:

```bash
oc create sa vault-auth -n default
oc create clusterrolebinding vault-auth-delegator \
  --clusterrole=system:auth-delegator \
  --serviceaccount=default:vault-auth
```

Generate a long-lived token for it and save it to a file (the `@filename` syntax in the next step reads from disk, not from an inline string):

```bash
oc create token vault-auth -n default --duration=87600h > vault-auth-token.jwt
```

### 3.3 Get the cluster's CA cert

This is **not** the homelab Vault CA — it's the CA that signs the OpenShift API server's own TLS cert, needed so Vault can trust the API server when it calls back to verify tokens:

```bash
oc get configmap kube-root-ca.crt -n default -o jsonpath='{.data.ca\.crt}' > cluster-ca.crt
```

### 3.4 Configure the auth method

```bash
oc whoami --show-server   # confirm the real API URL before using it below

vault write auth/kubernetes/config \
    kubernetes_host="https://api.homelab.jeremymr.dev:6443" \
    kubernetes_ca_cert=@cluster-ca.crt \
    token_reviewer_jwt=@vault-auth-token.jwt
```

Verify it took:
```bash
vault read auth/kubernetes/config
```

> **This step is the one that caused the initial `403 permission denied` on `/v1/auth/kubernetes/login` (Section 7).** The first pass omitted `token_reviewer_jwt` entirely — without it, Vault has no way to call TokenReview and rejects every login attempt regardless of role/policy correctness.

## 4. Phase 2: Vault Policy & Role for cert-manager

### 4.1 Least-privilege policy — only the signing path cert-manager needs

```bash
vault policy write cert-manager-policy - <<EOF
path "pki_int/sign/homelab-cert-role" {
  capabilities = ["create", "update"]
}
EOF
```

### 4.2 Kubernetes auth role, bound to cert-manager's actual controller SA/namespace

```bash
oc get sa -n cert-manager   # confirm the real SA name first

vault write auth/kubernetes/role/cert-manager \
    bound_service_account_names=cert-manager \
    bound_service_account_namespaces=cert-manager \
    policies=cert-manager-policy \
    ttl=1h
```

## 5. Phase 3: `ClusterIssuer` Manifest

### 5.1 Get the CA chain for `caBundle`

This lets cert-manager trust Vault's own TLS listener. Use the intermediate + root chain — **not** `homelab_root_ca.crt` alone (missing the intermediate) and **not** `fullchain.pem` (includes Vault's own short-lived leaf cert, which would go stale every renewal).

If `homelab-ca-chain.pem` from the original Vault PKI setup isn't saved anywhere locally, it can be re-pulled any time from Vault's public, unauthenticated CA endpoint — this is just public cert material, not a secret:

```bash
curl -sk https://192.168.0.201:8200/v1/pki_int/ca_chain -o homelab-ca-chain.pem
grep -c "BEGIN CERTIFICATE" homelab-ca-chain.pem   # expect 2 (intermediate + root)
```

Base64-encode it (single line, required for the CRD field):
```bash
base64 -w0 homelab-ca-chain.pem
```

### 5.2 The `ClusterIssuer`

```yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: vault-issuer
spec:
  vault:
    server: https://192.168.0.201:8200
    path: pki_int/sign/homelab-cert-role
    caBundle: <base64 output from above>
    auth:
      kubernetes:
        role: cert-manager
        mountPath: /v1/auth/kubernetes
        serviceAccountRef:
          name: cert-manager
```

Verify:
```bash
oc describe clusterissuer vault-issuer   # expect Ready: True
```

## 6. Phase 4: Example `Certificate` — Apps Wildcard

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: apps-wildcard
  namespace: openshift-ingress
spec:
  secretName: apps-wildcard-tls
  issuerRef:
    name: vault-issuer
    kind: ClusterIssuer
  dnsNames:
    - "*.apps.homelab.jeremymr.dev"
  duration: 2160h    # 90d
  renewBefore: 360h  # 15d
```

Once `Ready`, point the default `IngressController`'s `spec.defaultCertificate` at the `apps-wildcard-tls` secret so every Route under the wildcard (Grafana, ArgoCD, etc.) inherits it automatically — no per-app cert needed under normal Edge-terminated Routes.

## 7. Troubleshooting Log (as encountered, in order)

### 7.1 Argo CD couldn't sync the `Certificate`/`ClusterIssuer`

**Symptom:**
```
certificates.cert-manager.io "apps-wildcard" is forbidden: User
"system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot patch resource "certificates" in API group "cert-manager.io" in the namespace "openshift-ingress"

clusterissuers.cert-manager.io "vault-issuer" is forbidden: User
"system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller"
cannot patch resource "clusterissuers" in API group "cert-manager.io" at the cluster scope
```

**Root cause:** This is Kubernetes RBAC, not Argo's own project policy — the `homelab-platform` `AppProject` already whitelists `group: '*', kind: '*'`. The default OpenShift GitOps operator ClusterRole for the `argocd-application-controller` ServiceAccount doesn't include CRDs installed later by other operators (cert-manager's, and later ESO's/ACM's, will hit the same wall).

**Fix — grant `cluster-admin` to the controller SA once, applied manually:**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: openshift-gitops-argocd-application-controller-cluster-admin
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: cluster-admin
subjects:
  - kind: ServiceAccount
    name: openshift-gitops-argocd-application-controller
    namespace: openshift-gitops
```

```bash
oc apply -f gitops-cluster-admin-binding.yaml
```

**Important:** this cannot be applied *through* Argo CD itself — Kubernetes' RBAC escalation guard means a principal can't grant permissions it doesn't already hold, so the under-privileged controller can't bootstrap its own `cluster-admin` binding. It must be applied once, out-of-band, by an actual cluster-admin user, ideally right after the GitOps operator is installed and before/alongside the root Application (see `docs/gitops_bootstrap.md`, step 4).

**Trade-off, noted deliberately:** this makes anyone with push access to the GitOps repo effectively cluster-admin. Reasonable for a solo homelab; not a fine-grained RBAC posture.

### 7.2 `403 permission denied` on Vault Kubernetes auth login

**Symptom:**
```
Error initializing issuer: while requesting a Vault token using the Kubernetes auth:
error calling Vault server: Error making API request.
URL: POST https://vault.jeremymr.dev:8200/v1/auth/kubernetes/login
Code: 403. Errors: * permission denied
```

**Root cause:** initial `vault write auth/kubernetes/config` omitted `token_reviewer_jwt`. Since Vault runs outside the cluster, it has no in-cluster identity to fall back on and cannot call TokenReview without an explicit reviewer token — every login attempt is denied regardless of role/policy correctness.

**Diagnostics used to isolate it:**
```bash
docker logs vault --tail 50                       # Vault's own log has a more specific reason than the 403 cert-manager surfaces
vault read auth/kubernetes/config                  # confirm token_reviewer_jwt is actually set

TOKEN=$(oc exec -n cert-manager <controller-pod> -- cat /var/run/secrets/kubernetes.io/serviceaccount/token)
vault write auth/kubernetes/login role=cert-manager jwt="$TOKEN"   # replicate the exact failing call outside cert-manager
```

**Fix:** created the `vault-auth` reviewer ServiceAccount + `system:auth-delegator` ClusterRoleBinding, generated its token to a file, and re-ran `auth/kubernetes/config` including `token_reviewer_jwt=@vault-auth-token.jwt` (folded into Section 3.2–3.4 above as the corrected procedure). Confirmed fixed.

### 7.3 `CertificateRequest` failed — `the common_name field is required`

**Symptom:** the `Certificate` progressed through `Generated` (private key created) and `Requested` (`CertificateRequest` created), then failed:
```
The certificate request has failed to complete and will be retried: Vault failed to sign certificate:
failed to sign certificate by vault: Error making API request.
URL: POST https://vault.jeremymr.dev:8200/v1/pki_int/sign/homelab-cert-role
Code: 400. Errors: * the common_name field is required, or must be provided in a CSR with
"use_csr_common_name" set to true, unless "require_cn" is set to false
```

**Root cause:** cert-manager generates CSRs using SANs only (`dnsNames`) and does not populate a Common Name unless `spec.commonName` is explicitly set on the `Certificate`. The `homelab-cert-role` was created (`docs/vault_pki_setup.md`) with `require_cn` left at its default of `true`, so Vault rejected the CSR for having no CN anywhere. This is a well-known cert-manager + Vault interop gap, not specific to this setup.

**Fix — loosen the role to allow SAN-only certs.** `vault write` replaces the entire role config, so the original fields are repeated alongside the new one:

```bash
vault write pki_int/roles/homelab-cert-role \
    allowed_domains="jeremymr.dev" \
    allow_subdomains=true \
    allow_ip_sans=true \
    max_ttl="8760h" \
    require_cn=false
```

cert-manager retries failed `CertificateRequest`s automatically — no need to touch the `Certificate` object once the role is updated; it should move from `Failed` to `Issuing` to `Ready` on its own.

**Alternative (not used, but valid):** add `commonName: "*.apps.homelab.jeremymr.dev"` to the `Certificate` spec instead of changing the role. Skipped in favor of the role-level fix since it covers every future SAN-only `Certificate` (e.g. the API server cert) without needing `commonName` set on each one individually.

## 8. Verification Checklist

```bash
vault read auth/kubernetes/config          # token_reviewer_jwt set, kubernetes_host/ca_cert correct
oc describe clusterissuer vault-issuer     # Ready: True
oc describe certificate apps-wildcard -n openshift-ingress   # Ready: True, Secret apps-wildcard-tls populated
oc get secret apps-wildcard-tls -n openshift-ingress -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -issuer -subject -dates
```

The last command should show the cert's issuer chaining to the homelab intermediate/root, and an expiry consistent with the `Certificate`'s `duration`.

## 9. File/Secret Inventory

| File | Contains | Committed to Git? |
| :--- | :--- | :--- |
| `cluster-ca.crt` | OpenShift API server's CA (for Vault's k8s auth config) | No — local/operational only |
| `vault-auth-token.jwt` | Long-lived reviewer SA token | **No — treat as a secret, do not commit** |
| `homelab-ca-chain.pem` | Vault intermediate + root CA (public) | No, but safe to regenerate anytime via `pki_int/ca_chain` |
| `ClusterIssuer` / `Certificate` manifests | No secrets, just config/references | Yes — safe and intended to live in the repo (e.g. alongside the `cert-manager` chart) |

Nothing in this doc requires committing private keys or tokens to Git — the only Git-safe artifacts are the `ClusterIssuer`/`Certificate` YAML and the `ClusterRoleBinding`, all of which are pure configuration with no embedded secrets (the `caBundle` is public CA material, not a private key).

## 10. Known Follow-ups

- The `ClusterRoleBinding` from Section 7.1 and the Vault reviewer SA/token from Section 3.2 were applied manually and are not yet represented as manifests in the repo — consider adding the `ClusterRoleBinding` YAML under `operators/` (applied pre-bootstrap, per `docs/gitops_bootstrap.md`) so it's at least version-controlled even though it can't be Argo-applied.
- The `ClusterIssuer`/`Certificate` manifests above aren't yet added to the `operators/charts/cert-manager` chart — currently applied ad hoc.
- API server serving certs (`api.homelab.jeremymr.dev`) still need separate handling via `HostedCluster` configuration rather than the `IngressController` — not covered here.
